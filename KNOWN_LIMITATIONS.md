# Known Limitations — Little Loop V1

This document is required by the V1 development sprint (Day 8) so that
honest engineering claims are not confused with verification claims.
Each item below states what was **actually** exercised in this build
environment versus what would normally require a physical device or a
browser I do not have access to.

## Build environment

- Host: Windows 10, Node 24.15.0, npm 11.12.1
- No iPhone, no Android device, no mobile emulator
- No real iOS Safari, no real Android Chrome
- No screen-recording hardware for end-to-end MP4 visual verification

The CI environment for this project is **only this Windows machine**, so
"verified" in the README and tests means "verified on Node 24 + jsdom +
curl against the production preview server on `127.0.0.1`".

## iPhone Safari (iOS 17+)

**Not verified on a real device.**

What this means:
- The PWA install flow (Add to Home Screen) was not exercised.
- The native camera capture path (`<input type="file" accept="image/*"
  capture="environment">`) was not exercised on iOS Safari. It will
  open the camera by default there, but behaviour differs across iOS
  versions.
- HEIC/HEIF decoding relies on Safari's built-in support. The code
  accepts `image/heic` and `image/heif` MIME types and passes them to
  `createImageBitmap`. If a particular iOS version cannot decode the
  input, the user will see the "This image format is not supported"
  error from `image-processing.ts`.
- The MP4 download flow on iOS Safari is known to be inconsistent for
  large files because Safari may open the video in a new tab rather
  than downloading it. The export MP4 is currently a hard cut between
  frames at 720 × 1280, which keeps bitrate low.

Recommended validation before release:
- Install on a real iPhone, add to Home Screen, capture one photo,
  reload, confirm it persists.
- Confirm the MP4 download behaviour on a small one-photo export.

## Android Chrome 120+

**Not verified on a real device.**

What this means:
- The PWA install flow was not exercised.
- Camera capture (`capture="environment"`) was not exercised on
  Android Chrome.
- The service worker's offline-reload behaviour after the first
  install was not exercised.

Recommended validation before release:

## Desktop browsers (Chromium, Firefox, Safari)

**Partially verified.**

What was verified:
- The production build (`npm run build`) succeeds and emits
  `index.html`, `manifest.webmanifest`, `sw.js`, `workbox-*.js`, the
  icon set, and chunked assets including `dexie`, `jszip`, the FFmpeg
  placeholder chunk, and the `video-render.worker` chunk.
- `npm run preview` boots Vite preview on `127.0.0.1:4173` and serves
  the bundle. `npm run smoke` curl-verifies `/`, `/manifest.webmanifest`,
  `/sw.js`, `/icons/icon-192.png`, `/icons/icon-512.png` all return
  HTTP 200 with the expected MIME type and content.

What was **not** verified end-to-end on a real desktop browser:
- Visual rendering of the React UI (we did not launch a headless
  Chromium for this V1 cycle).
- The IndexedDB layer in a real browser engine (we have jsdom +
  fake-indexeddb tests, which is not the same as a real browser's
  IndexedDB implementation).
- The full MP4 render in a real browser using `ffmpeg.wasm`.
- Replace / delete / restore flows with real photos.

## FFmpeg / MP4 rendering

The `video-render.worker.ts` is shipped and the production build emits
its chunk (`dist/assets/video-render.worker-*.js`, ~6 KB). What is and
isn't verified:

- **Verified**: the `letterboxFit` math, per-speed frame counts, total
  frame count, and the typed Worker message protocol. These are
  exercised by `tests/unit/export-renderer.test.ts`.
- **Not verified end-to-end**: the FFmpeg core download from
  `unpkg.com/@ffmpeg/core@0.12.6/dist/umd/`, the actual MP4 encode, and
  the resulting file playing in a real player. FFmpeg core downloads
  require cross-origin isolation (COOP/COEP) or the Single-Threaded
  fallback to work consistently across browsers. If MP4 fails in a
  given browser, the spec permits an explicit WebM fallback labelled as
  such — that fallback is **not** implemented in V1 because we have not
  yet observed the failure on a real browser.
- **Lazy-load**: FFmpeg is loaded only when the user starts an export,
  per the spec. The first export will incur a CDN download of the
  ffmpeg-core JS and WASM (~30 MB combined). Subsequent exports will
  hit the browser HTTP cache.

Recommended validation before release:
- In Chrome on a desktop, open the production preview, import at least
  three photos, export them, save the MP4, play it locally. Confirm
  playback and chronological order.

## Service worker and offline

The service worker is generated by `vite-plugin-pwa` with the
`autoUpdate` strategy. The `precacheAndRoute` glob covers
`**/*.{js,css,html,svg,png,ico,webmanifest}`. What is and isn't
verified:

- **Verified**: the SW file is emitted at `dist/sw.js` with
  Workbox precache contents covering 15 entries (~386 KiB).
- **Not verified**: that the SW actually installs and caches on a
  real device, that offline-reload returns the cached app shell, and
  that the SW correctly handles updates.

## Test-suite caveats

- `tests/setup.ts` swaps `globalThis.Blob` and `globalThis.File` with
  Node's native classes from `node:buffer` because jsdom's Blob/File are
  stubs without `arrayBuffer()` / `text()` / `stream()`. This means the
  test environment is NOT a faithful model of browser Blob behaviour.
  Production code is real-browser code; the tests are smoke checks of
  the persistence and validation logic, not end-to-end coverage.
- The test that calls `processImageFile` uses a stub
  `createImageBitmap` returning a 1×1 mock. The full decode + resize
  + JPEG quality path is therefore not exercised by the unit tests.

## Privacy claim

The privacy claim ("photos stay on this device unless you choose to
export them") was verified at the **source level**:

- No `fetch` calls in `src/` send blobs, files, photos, or images.
- No `XMLHttpRequest`, no `navigator.sendBeacon`, no `FormData`
  upload.
- No analytics SDKs, no OAuth flows, no Google API calls.
- The only outbound network surfaces are the static asset fetches and
  the FFmpeg CDN load (described above).

This was verified by grep over `src/` and `dist/`. It is a strong
static guarantee, not a runtime guarantee.

## Things V1 explicitly does NOT include

These are excluded by spec and intentionally not present:

- User accounts
- Cloud sync
- Google Drive / Google Photos integration
- Notifications or reminders
- Social feeds / public sharing pages
- Comments or family collaboration
- AI captions or facial recognition
- Music licensing or in-app audio
- In-app photo editing
- Growth charts
- Multiple children / multiple timelines
- Server-side rendering
- Analytics or advertising

If any of these appear in a feature request, they belong in a
hypothetical V2, not V1.
